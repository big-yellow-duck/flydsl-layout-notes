## Per-lesson matmul comparisons

Each matmul solution and completed practice runs its own kernel against GPU `torch.matmul` after correctness, using the shared helper in `examples/matmul_benchmark.py`. Inputs/output remain BF16 on the GPU at M=N=K=1024. It reports milliseconds and effective TFLOP/s, excludes allocation and compilation, and takes the median of five batches after three warm-ups. `--repeats` defaults to 20 launches per batch.

Default `--timing auto` first tries GPU events; if any compared implementation has unavailable event timing, every row is retimed with synchronized host batches. This prevents mixing timing methods within a comparison. The fallback and host overhead are printed. Explicit `--timing gpu-event` preserves unavailable results without fallback; `--timing host` selects host timing directly. `--check-only` omits performance measurement. Course-wide checks set this mode for matmul automatically.

## Stage 06: LDS swizzling, padding, and counter evidence (2026-11-03)

The new [06-lds-swizzle lesson](lessons/01-gpu-programming/13-matmul/06-lds-swizzle/README.md) builds directly on stage 05's four-wave `(2,2,1)` WMMA kernel: fixed 1024³ BF16 inputs/output, FP32 accumulation, 32×32×32 block tiles, and 128 threads. A tracing-time native-view helper specializes A's LDS layout as packed, `Swizzle<3,3,3>` composed with packed, or row stride 40 with an enlarged allocation. B, MMA ownership, global copy ownership, and the two barriers remain fixed. The swizzle uses `fx.static(fx.SwizzleType.get(3,3,3))` and `fx.make_composed_layout`, checked against installed FlyDSL 0.4.1 `expr/primitive.py`. It XORs element-offset bits 6–8 into bits 3–5 while preserving aligned eight-BF16 staging chunks. Both staging and operand partitioning retain the layout. See the [pinned API source](https://github.com/ROCm/FlyDSL/blob/888d7d80528f0cf2abab8a86610d5ccca47f205d/python/flydsl/expr/primitive.py), [AMD bank-conflict description](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/performance_optimization.html), and [rocprofv3 collection reference](https://rocmdocs.amd.com/projects/rocprofiler-sdk/en/latest/how-to/using-rocprofv3.html).

The [recorded evidence](lessons/01-gpu-programming/13-matmul/06-lds-swizzle/results/2026-11-03-gfx1151/README.md) includes original counter CSVs, agent metadata, final ISA, worker logs, counter definitions, profiler version, commands, source hashes, and two complete timing captures. Measurements used AMD Radeon 8060S Graphics (`gfx1151`), FlyDSL 0.4.1, ROCm SDK 10.0.0, ROCprofiler-SDK 1.3.5, and PyTorch 2.13.0+rocm10.0.0. The driver requires ten matmul dispatches per layout: two full-output checker dispatches, three warm-ups, and five samples. It verifies the derived ratio against raw reduced counters with a positive denominator. `LDSBankConflict = 100*sum(SQC_LDS_BANK_CONFLICT)/sum(SQC_LDS_IDX_ACTIVE)` was 46.153846% packed, 30.769231% swizzled, and 6.666667% padded. The numerator decreased from 6,291,456 to 4,194,304 or 524,288. Counter definitions label these events emulated/C1; this is the SDK's conflict ratio, not a wall-time fraction or a count of conflicting lanes. Values were identical across sampled dispatches and repeated captures.

ISA retained 128-bit global loads/staging stores and two WMMA sites per K-stage loop for all modes. The swizzle scalarized A loads: total scalar BF16 LDS sites rose from 32 to 64 while four `ds_load_b128` sites disappeared. Dynamic LDS instructions rose from 4,980,736 to 8,650,752; VGPRs rose from 56 to 88. Padding retained the packed instruction widths/register count and added 512 LDS bytes (4096 to 4608). ## Stage 07: interleaved global loads and current-tile WMMA (2026-11-03)
